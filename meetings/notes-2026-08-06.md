We have to resolve the merge conflict between all three of these proposals: Amount, this one, and sequence-units.

SFC: We discussed this for almost an hour at the JS Numerics call. My main takeaway: .value returning a numeric primitive is not a good idea. Also: it’s OK for .value to return a single type. It’s already polymorphic. Returning a non-primitive object seemed OK to people. That’s the direction I’d like to explore further. We also have .values could return an array or object. In the intl-sequence-unit proposal, we propose an object structure. So we could put something like that in the .value field. That would help with interop in the case of sequence units. I think this is fine. I think we can leverage a lot of the existing decisions we’ve made.

EAO: IIRC we ended up agreeing that an array of .values in the same order as they are in the -and- would help us. That is, an object with the same number of properties as the split -and- identifier.

SFC: I think array is something we had considered. We decided early on on a structure. Did we explicitly discuss an array?

EAO: I recall something like this in Amesteram, but not sure if that was in plenary or outside plenary.

SFC: (pulls up 402 issue #398) https://github.com/tc39/ecma402/issues/398

RGN: I think a primitive, non-canonical representation. Array is fine, but object would be fine. Just want uniformity.

SFC: In response to the different shapes proposed above, we got stage 2 with proposal (A). But now people are proposing something like ( C ). If the JS Numerics champions seem OK with that, then let’s proceed with that.


SFC: Can we mix numeric types in the array?

SFC: We want to format rational numbers in units. E.g. ¾ mile, ⅔ cup, etc. Often used in cooking with imperial measurements. How do we represent it? So “1 and ¾ mile”, use a sequence unit, “mile-and-quarter-mile”. Same for cup. One reason I like this approach: it’s compatible with our existing machinery. Adding Rationals to the language is a heavy lift. Even I don[t think I could make a compelling case. Also, if we add rationals just in Intl, we could have a rational protocol. But that’s also a niche thing, sort of poking a hole in the design. We leverage existing infrastructure. No need to add anyth9ng special. Just need to define new units, which have special formatting behavior. No API changes.
